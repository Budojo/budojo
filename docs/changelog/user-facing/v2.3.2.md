# v2.3.2 — 2026-05-10

A two-fix release plus a wave of behind-the-scenes legal-docs work. The two visible fixes:

1. **Attendance page sort-by-belt was hiding most of the roster.** Luigi reported that on `/dashboard/attendance` (the daily check-in page), clicking the Belt column header to sort silently dropped every belt above white — only the white belts showed and there was no paginator to walk further. Fixed: the page now paginates at 20 per page and the paginator surfaces below the table whenever you have more than 20 active athletes.
2. **Privacy policy used to claim "daily database backups with 30-day retention".** That claim wasn't true — the automated backup strategy is still being implemented before the first real customer data lands. Reworded the bullet on `/privacy` and `/privacy/it` to match reality: "an automated database-backup plan planned to be implemented before any real production customer data is collected." Stopped over-promising; aligned the public claim with what the DPA template and infrastructure runbook already say internally.

Everything else is invisible-to-users compliance and documentation hardening: a Data-Protection-Impact-Assessment for medical certificates, an academy-offboarding runbook, the actual Play Store listing copy ready to paste into Google Play Console, and a fresh test layer pinning that medical certificates flow correctly through the GDPR access + erasure paths.

## 🐛 Attendance — sort-by-belt no longer hides the rest of the roster

This was a real bug Luigi (a customer) ran into. With more than 20 active athletes and the table sorted by belt ascending, the white-belt cohort would exhaust the per-page slice before any blue / purple / black belt could appear, so the rest of the roster was invisible from the UI. Filter strip changes had the same shape — narrowing on a belt and then sorting could drop you onto a phantom empty page.

The fix:

- The page now requests one server-paginated slice at a time and binds the paginator chrome (page numbers + arrows below the table) to the result. You see the same thing you'd see on the main athletes list.
- Searching, filtering by belt, or clicking a sort header always snaps you back to page 1 — so a narrowing filter never leaves you on an empty page.
- The paginator only renders when you actually have more than 20 athletes, so under that threshold the page looks identical to before.

If you were running into this, the fix lands automatically; nothing for you to do.

## 🐛 Privacy policy — "daily backups" claim corrected

The bullet under "Modalità di trattamento e misure di sicurezza" (§ 5) used to say "Backup giornalieri della base dati con retention 30 giorni" / "Daily database backups with 30-day retention". That was stronger than reality — the automated backup strategy is documented as an explicit prerequisite for real production customer data, but it isn't yet active.

The bullet now reads "Piano di backup automatizzato della base dati in implementazione prima della raccolta di dati reali in produzione" / "An automated database-backup plan planned to be implemented before any real production customer data is collected." It points at the DPA template § 8 and the production-deployment runbook for the technical decision (DigitalOcean Managed DB vs `mysqldump` cron vs droplet snapshots) that's still being made.

This is a transparency-improvement, not a security regression — nothing about how your data is handled changed; only what we say about it. The actual backup strategy is the next item on the production-readiness checklist, and this release entry will get a follow-up note when it lands.

## 🔧 Behind the scenes — legal docs + medical-cert test coverage

Several documents and tests landed this cycle that aren't visible inside the app but matter for compliance posture:

- **DPIA-lite for medical certificates** (Data Protection Impact Assessment, GDPR Art. 35) lives at `docs/legal/dpia-medical-certificates.md`. It walks through the risks, mitigations, and the strategic A-vs-B choice between keeping medical-cert PDFs inside Budojo (with encryption + audit) vs storing only `valid yes/no + expiry` and letting the academy's own storage hold the file. Recommendation is option B until traction; the choice itself is still pending.
- **Academy-offboarding runbook** at `docs/operations/academy-offboarding.md` walks the manual procedure for when an academy customer ends the contract — three windows (T-30 notice, T0-T+30 grace export, T+30 purge) with explicit steps for each.
- **TWA runbook rewritten** so it describes the actual `/.well-known/assetlinks.json` flow (static file under the SPA bundle, edited via PR, served by Cloudflare Pages) instead of the retired Laravel-routed env-driven implementation that was deprecated in v2.3.1.
- **Play Store listing copy** drafted in English and Italian at `docs/mobile/play-store-listing.md`, including the Data Safety questionnaire answers — so when the Android app ships, the listing is paste-ready.
- **Medical-certificate test coverage** added to the GDPR Art. 15 export and Art. 17 erasure flows. The flows already did the right thing; the tests pin the behavior so a future refactor can't silently regress the special-category-data handling.

None of this affects what you see on the dashboard today; it's the compliance and documentation foundation that the next batch of features (audit log, encryption-at-rest, multi-user invites) will build on.
