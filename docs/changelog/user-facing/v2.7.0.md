# v2.7.0 — 2026-05-12

The biggest release since v2.0. Two new product surfaces land together: **the athlete portal** (every athlete can now sign in and see their own attendance / payments / documents / profile, plus a "My academy" card) and **the community feed** (a Facebook-style timeline of what's happening at the academy — belt promotions, owner-posted events, reactions, comments, RSVPs). And three new categories of inbox notification tie the two surfaces together so nothing important gets missed.

## ✨ The athlete portal — every athlete now signs in

Until v2.6 the only person who used Budojo was the academy owner. From this release every athlete you've invited gets their own login and lands on `/dashboard/me/...`:

- **`/dashboard/me/profile`** — the athlete's own profile card with avatar, name, handle, belt, contact details. Edit mode (gear icon top-right) opens a clean reactive form: first/last name, handle (with the same `[a-z][a-z0-9._]{2,29}` validation the owner-side uses, "@mariobjj" not "MarioBJJ_"), and the standard handle-taken / consecutive-dots / trailing-dot error states.
- **`/dashboard/me/academy`** — a read-only "My academy" card showing the school's name, owner, location, and the athlete's own membership status (joined date, current belt).
- **`/dashboard/me/attendance`** — the athlete sees their own attendance log: month-by-month grid of training days, percentage of classes attended, and an at-a-glance streak indicator.
- **`/dashboard/me/payments`** — the athlete sees their own payment history, in their language's currency format (€1.234,56 for IT, €1,234.56 for EN), with a friendly month label and the status pill.
- **`/dashboard/me/documents`** — the athlete sees their own medical certificates and other documents. Expiry status (Valid / Expiring soon / Expired) right on the row. Expired today is shown as expired (inclusive boundary).
- **`/dashboard/me/feed`** — the new community feed, see below.

The owner-side dashboard is unchanged — you keep managing everyone the same way. The portal is purely additive: athletes you've already invited will now see their own version of the data starting next sign-in.

## 🎉 The community feed

`/dashboard/me/feed` (and also reachable for owners) is a timeline of academy life. Three kinds of post:

- **Belt promotions** — when an owner changes an athlete's belt (from the athletes admin), a celebration post is automatically created in the feed with the athlete's name + old belt → new belt. Auto-deleted if you ever delete the athlete.
- **Events** — open mats, seminars, in-house tournaments. Owners can post them (more on this below); athletes see the card with title, when, where.
- **Announcements** (foundation laid for future) — the schema is in place; owner-side composer for free-form announcements ships in a follow-up.

Each post carries the author's name, avatar, handle, and belt badge — the same `<app-user-flair>` you see across the SPA, with a short-fallback ("Mario R.") when no handle is set.

### 👏 Reactions

Tap **👏 Clap** or **🙏 Pray** at the bottom of any post. The button flips to its active state immediately (optimistic UI) and the count updates on the post. Tap the same emoji again to remove your reaction; tap the other one to switch. Quick double-clicks are serialized server-side so the row never ends up in a half-toggled state.

### 💬 Comments

Each post has a one-level **Comments** section that expands on tap. Write a comment (up to 500 chars), see it appear in the list, delete your own with the trash icon. The post's comment count updates inline as comments arrive or are deleted — no full refresh needed.

### 📅 Event RSVPs

Event posts carry three RSVP buttons: **Yes / Maybe / No**. Tap to commit, tap again to clear, tap a different one to switch. The headcount on the event card updates in real time as RSVPs flow in (optimistic locally, race-safe server-side).

## 🔔 New inbox notifications

The bell in the dashboard topbar (introduced in v2.6) now surfaces three new community-flavoured notification kinds:

- **Someone replied to a thread you're in** — `community_reply`. Default-on. When you comment on a post and someone else later comments on the same post, you get an inbox row pointing back to the thread. The author of the new comment never gets notified about their own post; you also don't get notified about your second comment in the same thread.
- **A teammate earned a new belt** — `community_belt_celebration`. **Default-OFF** — the every-athlete blast radius is wide, so you have to opt in explicitly on `/dashboard/profile` to receive these. Once on, every belt promotion in your academy lands as an inbox row (except for the one you recorded yourself).
- **Your academy posted a new event** — `community_event_new`. Default-on. When the owner posts a new event to the feed, every athlete in the academy gets an inbox row deep-linking to the event card.

All three are gated server-side and surfaced as toggles in `/dashboard/profile` → Notifications. The toggles persist instantly with optimistic UI.

## 🔧 Owner-side event creation

`POST /api/v1/community/events` is now a real endpoint — owners can create events programmatically (or via the upcoming SPA composer in a focused follow-up). V1 ships create only; edit / cancel surfaces are V2. Body shape: title (required, 1–120 chars), description (optional, max 2000), starts_at (required ISO 8601 date-time, re-serialised to canonical UTC), optional location text + lat/lon (V2 map view-ready) + max attendees.

## 🔧 Behind the scenes

- **Race-safe reaction toggle** — read-then-upsert on the unique `(post_id, user_id, emoji)` constraint now runs inside a DB transaction with a shared lock + caught `QueryException` on concurrent races. Worth knowing for anyone wiring similar UI primitives.
- **Optimistic UI as the canonical pattern** — every interaction in the new feed (reactions, RSVPs, comments) is wired through a per-post `Subject` + `switchMap` that serializes rapid clicks and rolls back the UI on server error. Same shape across all three flows.
- **Belt-promotion observer** — the auto-post on a belt change happens via an Eloquent observer wired with the `#[ObservedBy]` attribute. The observer skips console / seeder context (no authenticated user to attribute), so seeded belt changes don't generate stale celebration posts.
- **Default-off categories** — the notification preferences system grew a new `defaultOff()` mechanism (consulted by `NotificationPreferences::isEnabled` for the absent-key fallback). The Belt celebration category uses it; absent-key recipients are NOT notified until they explicitly opt in. The SPA panel surfaces it with an "Off by default" hint.
- **Stable payload key set** — `community_posts.payload` now carries a fixed shape per post type, pinned by a schema test. Adding a new post type or a new payload field involves updating both the factory and the schema test in the same diff.
